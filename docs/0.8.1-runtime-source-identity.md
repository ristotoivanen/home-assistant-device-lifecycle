# BL-04 Runtime source authorization — approved Option A

Owner decision: 2026-10-15. Local implementation and commits are authorized;
push, PR creation, merge, release, production HA operations and unrelated baseline
work are not authorized. This document records the implemented contract, not a
release approval. Independent acceptance and the three-version test matrix are
required before closing BL-04.

## Configuration contract

Runtime ConfigSubentry data gains `source_identity`, independently versioned at
`version: 1`. It contains a fresh `authorization_id`, `registry_id`, `domain`,
`platform`, `unique_id`, `config_entry_id`, `config_subentry_id` and `device_id`.
The nullable owner/subentry/device IDs are compared exactly. Unknown versions,
malformed bindings and missing bindings never authorize observation.

A new tracker captures the selected registered source at form submission, before
waiting for an Asset binding reservation. It revalidates that exact selection
after the wait; replacement retains the form with `source_changed_during_save`
and requires review and resubmission. No later occupant inherits that consent.
Both creation and reconfiguration watch for source removal or identity events
during their awaited save preflight, including remove/return with identical
logical IDs and legacy trackers without any old binding. Prior nested events
drain before final validation. A reconfiguration also compares the live binding
against its immutable preflight snapshot: neither a settings edit nor an earlier
confirmation may overwrite a concurrent revocation or newer authorization.
Any such gap retains the form and requires a fresh submission. Presentation-only
changes do not revoke consent; cancellation removes the temporary observer and
releases any newly held creation reservation. These temporary guards refuse stale
consent only; the ConfigSubentry binding remains the durable authorization.
Reconfiguration requires **Confirm the selected source identity** whenever the
source changes or its authorization is absent, invalidated or mismatched. Checking
this box also deliberately renews an unchanged source's authorization. The nonce
makes confirmation an actual ConfigSubentry update even after an ABA return or a
same-address replacement. It imposes no uniqueness constraint on sharing a source
between different Assets.

The existing `runtime_data_version: 1` retains only its initialization-provenance
meaning. Reconfiguration preserves its presence, absence and value. This patch
changes neither canonical Store 4.1, ConfigEntry version, manifest/integration
version, Asset ownership, UUID resolution nor Runtime restore/import provenance.

## Pauses and recovery

Legacy trackers without a binding retain their entity, history and canonical
Runtime but pause until explicit confirmation. A State without an Entity Registry
row cannot be durably authorized: select a registered source. Editing the
thresholds of an unchanged missing source remains possible; it does not authorize
that source or resume observation.

Identity is checked at setup, before processing State activity, display projection
and checkpoints, and on relevant registry events. Retirement, removal, shutdown
and unload all pass through the same guarded interval-sealing boundary. A record
ID, logical tuple, origin or device reassignment requires explicit authorization;
name and other presentation-only changes do not. Ordinary unavailable/unknown and
missing State values do not revoke an otherwise valid registry binding.

Rename policy: pause and explicitly select/confirm the anchored row's new address.
The code verifies the registry record and logical-origin guards, and never follows
whatever now occupies the old address. Automatic rename following is not provided.

A detected discontinuity is latched immediately, before waiting for the Runtime
lock. HA can defer nested registry events while eagerly starting another coroutine.
Every asynchronous interval-sealing path therefore yields before acquiring the
Runtime lock, allowing those prior registry notifications to be processed before
new time is classified as proven pending. Synchronous projection also compares
the current immutable registry-row revision with the last processed revision:
it excludes the unsealed tail while a revision is pending. After the event barrier, each sealing operation validates and adopts a verified
presentation-only revision under its own Runtime lock before sealing. It never
waits for a separate refresh task to win that lock: unload/removal must retain
that valid interval. Removal or identity events latch revocation first. This session revision guard supplements
the durable binding and never establishes source authorization. It clears the unsealed active tail, preserving committed time and every
already sealed valid pending delta. An exact timing boundary cannot be invented
from a delayed callback. Historical committed Runtime is never subtracted or reset.

A valid binding gains `invalidated: <reason>` through HA's ConfigSubentry API when
a gap is detected. This persisted revocation prevents automatic resumption if the
original row returns or the entry reloads/restarts. Stale callbacks cannot revoke
a newer authorization. Invalidation-only notifications do not reload the entry:
the existing paused writer keeps its pending retry state. An exact configuration
snapshot distinguishes this notification from subsequent user edits; this
transient scheduling hint is not an authorization store.

Runtime sensor attributes expose `runtime_source_status`, `runtime_source_state`
and `runtime_source_recovery`, separately from ordinary source availability. The
warning identifies the source and Asset and gives the recovery action. It is
emitted once per writer's transition, not on every periodic retry. In the Runtime
subentry's reconfigure form, select the intended registered source and explicitly
confirm its current identity. English and Finnish forms explain that accumulated
Runtime is retained and uncertain elapsed time is excluded.

Before a changed configuration is saved, the flow strictly checkpoints the old
writer outside the Store lock. If persistence fails, the form remains open with
`runtime_pending_retry`; the authorization and valid pending Runtime remain with
the existing writer. Correct the storage problem and resubmit the form. After
awaiting this preflight, a freshly confirmed binding is revalidated so a replacement
during the write cannot inherit the approval. Reload then uses the existing BL-03
unload/durability fence. No Store protocol is bypassed or weakened.

## Limits

Registry identity authorizes a logical source. It cannot attest physical hardware
when an upstream integration reuses every logical identifier. Changes occurring
entirely while HA is stopped with all registry guards restored are likewise not
observable. No physical continuity guarantee is claimed.

HA owns normal ConfigSubentry/registry persistence, including delayed saves and
shutdown flushing. This patch does not create an independent transaction across
HA configuration, registry backups and canonical Runtime. Restoring inconsistent
backups normally pauses on a missing/mismatched binding; a backup restoring all
logical identities cannot reveal erased history. Downgrading to an older binary
that ignores `source_identity` removes this protection. Registry-less sources
require a separately approved stable authorization contract before support.

Healthy Runtime crash-loss bounds are unchanged. During persistence failures,
valid pending deltas remain in memory and there is no crash-loss bound. A manual
HA reload that independently fails its unload gate may enter HA's existing
`FAILED_UNLOAD` state; the reauthorization form's preflight prevents taking that
path for a known pending-write failure. This patch does not alter HA's state
machine or claim exhaustive scheduling/power-loss coverage.

## Verification

The permanent RED commit reproduces 36 failures and 8 controls on unchanged
baseline `ac171bdc5df66d137adb7d77bffd1a3b8d1d45e7`: 32 numeric safety failures,
2 registry-less policy failures and 2 missing same-address authorization updates.
Original external evidence is preserved outside the repository.

Independent review rejected the first otherwise-green implementation after finding
creation/reservation replacement and nested-event ABA sealing races in both modes.
Those numeric REDs were preserved and converted to permanent tests before fixing
the approval boundary and deferred-sealing/revision guard. A second independent
review then found presentation-only nested changes losing valid elapsed at a
lifecycle boundary; fourteen permanent REDs preceded the correction that validates
the processed revision in the sealing operation itself. Stale projection after
parent removal also has a permanent safety test. Nested ABA tests cover explicit
and periodic checkpoint, unload preparation, direct removal, retirement, shutdown
and actual ConfigEntry unload, as well as synchronous value projection.

The continuation's final v4 review rejected a reconfiguration race: an awaited
preflight could let a captured binding overwrite a later revocation, even when
the form had included confirmation. Eight permanent numeric REDs cover Runtime
lock waits and real blocked atomic writes in both modes. Four further REDs prove
that initial creation and legacy confirmation also require a selection-gap guard
when no old binding exists. Twelve presentation controls retain valid time.
Creation cancellation also verifies observer and reservation cleanup.

The permanent suite exercises ON-state and POWER with real HA platform setup,
registry operations, events and isolated canonical Store files. It covers legacy
confirmation, malformed/versioned bindings, same-owner replacement, rename,
origin changes preserving row ID, ABA return, queued callbacks, real unload,
failed reauthorization persistence, readback/write failures and cancellation.
The retained probe label `cancel-after-write` cancels while the atomic writer is
blocked before its write; a separate test proves durable file contents before
requesting cancellation during readback.

Eight fresh Python-process scenarios per HA version boot the version-pinned HA
ConfigEntries and Entity/Device registries from real serialized synthetic files:
valid, replacement, legacy and previously invalidated/returned sources, each in
both modes. The test harness supplies source States and a deterministic monotonic
clock. It does not launch a production HA server or emulate source hardware.

Final execution counts, exact source freeze, independent acceptance and residual
risks are recorded in the external implementation evidence package. Neither green
CI nor these tests alone approve a release.

The 2026-10-16 continuation additionally verifies cancellation of the actual
reauthorization FlowManager task while its persistence preflight owns a blocked
write: cancellation drains the valid write, leaves authorization unchanged, and
retry commits the valid delta once before resuming the approved source.

Both modes also run three sequential child OS lifetimes: an original observer
loads and persists 1040 and exits; a registry-only HA child replaces the source
at the same address and exits; a new observing HA child loads that persisted
replacement, excludes its unauthorized 30 seconds, and explicitly reauthorizes
it through the real ConfigSubentry flow before adding only 20 future seconds
(total 1060). Each process exit is awaited before creating the next; PIDs and
serialized observations prove the sequence. The new approval is checked in the
actual ConfigEntries file after the final child exits. Together with the eight
standalone startup cases, this executes fourteen child OS processes per HA
version. The parent orchestrator remains alive with its original entry unloaded;
it never observes the source during those child lifetimes. This uses HA's core
test runtime, actual registry/Store APIs and startup/stop events, not the full
production server/network bootstrap or physical source clients.
