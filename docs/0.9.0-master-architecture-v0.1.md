# Device Lifecycle 0.9.0 — Master Architecture v0.1

> **Status: WORKING DRAFT — NOT APPROVED / NOT FROZEN.**
> **Purpose:** establish an explicit common contract for Purge, tombstones, portability, verified backup/restore, recovery, migration and hardening.
> **Authority:** subordinate to the accepted 0.8.0 / Store 4.1 implementation and its frozen contracts until this document is reviewed and approved. Statements tagged **CANDIDATE** or **OPEN / BLOCKING** are proposals, not implementation permissions.
> **Scope of this change:** documentation only. No production code, Store migration, ConfigEntry change, release, or deletion is authorized by this draft.

## 2. Non-negotiable invariants

1. An Asset represents one physical object. Its canonical \`asset_uuid\` and public \`DLxxxx\` identity never change; Asset IDs are monotonic and never allocated again. No Purchase, HA Device, Runtime configuration, Archive state, or Maintenance schedule defines Asset identity.
2. Archive is reversible management state, **not** physical Lifecycle status or deletion. Store 4.1 Archive/Maintenance semantics stay unchanged unless an explicitly versioned, separately reviewed migration proves the change.
3. Lifecycle, Replacement, Purchase membership, Maintenance history, Runtime totals, and field provenance retain their current invariants. Unknown information remains unknown; never infer a historical measurement or link.
4. Each persistent mutation must validate a detached candidate and publish only a verified durable result. Persistence ambiguity fails closed. The existing Store mechanism is authoritative only for the **Device Lifecycle Store file**, not for all HA-owned state.
5. An external HA device/entity ID is installation-local. A matching name, area, entity ID text, or numeric identifier does not prove it is the same physical object after import.
6. A destructive operation needs an accurate impact preview and deliberate confirmation. No hidden overwrite, merge, repair-by-guessing or automatic Purge.
7. Failure and interruption paths are product behavior, not implementation afterthoughts. Until proven otherwise, a partially executed multi-owner operation must be treated as **unresolved**, not reported as successful.
8. User-facing flows remain simple, English and Finnish; internal UUIDs, schema mechanics and journals are not normal workflow prerequisites.
9. Restore and Purge must not create orphaned or ambiguously owned Device Lifecycle entities or take ownership of third-party HA devices.

## 3. Data authorities and interoperability boundary

| Domain | Current authority | 0.9 design treatment |
| --- | --- | --- |
| Canonical Assets, Purchases, allocation counter, Lifecycle, Replacement, Archive, Runtime totals, Maintenance, provenance | Device Lifecycle private, versioned HA Store | Exact, validated, consistent export; version-aware restore; no inferred values |
| Parent ConfigEntry and Purchase/Runtime ConfigSubentries | Home Assistant ConfigEntry system | Semantic, explicitly allowed fields; recreated/updated through supported HA APIs; never import opaque raw \`.storage/core.config_entries\` |
| Device Lifecycle Asset Devices | HA Device Registry; stable identifier derived from \`asset_uuid\` | Reconcile *owned* devices after preflight; no takeover of unrelated devices |
| Device Lifecycle entities, unique IDs and entity registry metadata | HA Entity Registry and Device Lifecycle projection | Preserve deterministic \`unique_id\`; reconcile owned entries; existing \`entity_id\` retained where provably safe; cross-instance \`entity_id\` not guaranteed |
| External HA device references, area IDs, Runtime source entity references | Other HA integrations / target installation | Keep source reference as evidence, but unresolved until safe mapping; no name-based automatic rebinding |
| Recorder history, external devices, HA user customizations, unrelated config, backups | Home Assistant or other systems | Explicitly **outside** Device Lifecycle canonical backup; explain consequences to users |

Home Assistant Core 2026.8 introduced single-ConfigEntry/at-most-one-ConfigSubentry Device Registry ownership. HA 2026.10 further enforces deprecated ownership accessors. The 0.9 implementation must obey those APIs and ownership checks; see:
- https://developers.home-assistant.io/blog/2026/07/21/device-registry-single-config-entry/
- https://developers.home-assistant.io/blog/2026/09/15/device-entry-config-entries-deprecation/
- https://developers.home-assistant.io/docs/device_registry_index/

**Existing implementation checkpoints:** \`storage.py:DeviceLifecycleStore\` uses atomic writes and readback verification; \`AssetStoreManager._async_mutate_reporting\` serializes Store mutation; \`exposure.py\` preflights owned registry projections and uses compensating best-effort rollback; \`__init__.py\` manages setup/unload and Runtime checkpoints. These are *not yet* a transactional system spanning all HA owners.

## 4. Export/backup contract (candidate architecture)

**CANDIDATE: versioned logical package, not a raw HA storage dump.** Its exportable domains must cover the seven Store 4.1 collections and all schema-owned fields, including allocation state, archives, history, Runtime totals, and future tombstones. It must also carry sufficient **semantic** Device Lifecycle ConfigSubentry information to allow a coherent supported restoration. Export version is distinct from the internal Store version.

Required logical components, with final names/serialization **OPEN**:
1. Manifest: format version, source integration version, source Store version, minimum reader compatibility, creation time, scope, object counts and declared limitations.
2. Canonical payload: validated full logical Store snapshot; no partial collections; stable UUID, \`DLxxxx\` and allocation counter.
3. Configuration manifest: allowlisted parent/subentry types, stable references (e.g. Purchase UUID, Asset UUID), relevant Runtime mode/thresholds and source-reference descriptors, *without raw HA IDs as portable identities*.
4. Integrity manifest: deterministic serialization and SHA-256 over defined bytes (algorithm, exact coverage, canonicalization and size limits must be specified); checksum detects corruption but **does not authenticate origin**.
5. Compatibility and external-reference report: expected unresolved HA links and target requirements.

**Safety:** prohibit credentials, auth tokens, unrelated configuration and registry dumps. Audit free-text and URL fields (including \`receipt_url\`, notes, source descriptors) for embedded secrets; do not claim "secret-free" without an enforceable field policy. Backup may contain purchase values, serial numbers and personal notes and must be described as sensitive; encryption/access control are **OPEN**. A silently redacted export must not be called an exact round-trip.

**Consistency:** the existing Store mutex does not freeze ConfigEntry/ConfigSubentry operations or all Runtime writers. Define a bounded snapshot barrier that checkpoints active Runtime, stops new configuration mutations for the snapshot, revalidates source epochs/fingerprints, and either exports one coherent logical point-in-time state or fails visibly. No Runtime delta may be lost, reset or invented. Lock acquisition order and writer resume/cancellation semantics are **OPEN / BLOCKING**.

Export must be available from the UI as a downloadable file; its validation routine must also be reusable by import and automated tests. A successful export alone does **not** prove recovery.

## 5. Import/restore contract (candidate architecture)

**MVP restore mode: clean Device Lifecycle target only.** This includes an explicit preflight for empty DL canonical state, compatible supported parent entry state and absent conflicting DL registry identity. "Clean" means no existing DL data, not permission to delete unrelated HA information. No in-place destructive overwrite and no merge in MVP.

Proposed operational phases, **not yet an approved transaction algorithm**:

1. Parse under strict byte/structure limits; verify manifest, checksum, format/version and reject unsupported schema, corrupt/partial archive, duplicate IDs, inconsistent references, impossible allocations and identity collisions.
2. Build a complete, read-only dry-run plan: canonical differences, target ConfigEntries/Subentries, projected DL devices/entities, conflicting IDs, external references, unresolved mappings, user impact and supported recovery path.
3. Require explicit confirmation of the exact plan; fail if the target has drifted since preview.
4. Establish a durable recovery/transaction boundary **before any mutation**, fence Runtime writers and conflicting operations, and execute an ordered staging/apply protocol using supported HA APIs.
5. Verify both persisted canonical data and HA-owned side effects; activate only when internally consistent. On exceptions or process interruption, recover deterministically on next setup, or remain blocked with explicit Repair instructions if automatic safe resolution is impossible.
6. Retain structured, non-secret evidence of outcome; never display a partial restore as successful.

**OPEN / BLOCKING: cross-owner atomicity.** HA Store's per-file atomic save does not make ConfigEntries, Device Registry and Entity Registry one database transaction. Define an idempotent operation ID, durable journal/phase markers, ownership-sensitive compensation, recovery order, crash tests at every durable boundary and a clear activation gate. No "all-or-nothing" acceptance without proof across those owners and crash windows. Reusing the existing exposure best-effort rollback alone is insufficient.

**External references:** no automatic rebinding to a target HA device or source entity simply because name, entity_id or a local ID matches. Present unresolved links and require explicit selection/verification. Runtime tracking must remain inert/quarantined until its source and Asset association are valid; canonical Runtime totals remain unchanged. Cross-instance Recorder history and the original entity_id are not guaranteed portable. Same-instance identity continuity needs its own explicit test.

**Version compatibility:** specify forward-rejection, supported older-format readers/migration sequences and how a validated restore relates to Store migrations. Unknown versions fail closed. ConfigEntry v4 continuity is baseline, not a promise that it can remain v4.

## 6. Permanent Asset Purge and tombstones (candidate architecture)

Purge is exceptional and irreversible **within the current live dataset**, unlike reversible Archive/Restore. It must not be enabled before verified backup + clean-target restoration passes its release gate.

Preserve these already locked constraints from [ARCHITECTURE.md](../ARCHITECTURE.md#permanent-deletion--purge-09x):
- Archived Asset only; never while deployed; unresolved/active Runtime writer or configuration blocks.
- Active Maintenance dependencies, HA references and Replacement relationships require defined resolutions; do not silently mutate unrelated HA devices.
- Exact impact preview and explicit confirmation; user must know what disappears and what remains.
- Retire original UUID and Asset ID for the continuing dataset; allocation counter never decreases. A future Quick Create replay must not silently recreate a purged identity.
- Existing surviving historical references must stay interpretable; graph validation must account for deleted-reference targets.

**CANDIDATE:** a minimal, immutable deleted-Asset reference/tombstone containing canonical \`asset_uuid\`, \`asset_id\`, deletion timestamp and only additional fields proven necessary. It must never behave like an active Asset, create a device/entity, accept Runtime, or be selected in normal management. The model must define whether retained Purchase membership and historical Replacement edges reference tombstones or are rewritten through a traceable rule.

**OPEN / BLOCKING:** the complete dependency matrix for Lifecycle events, Purchases and membership, Replacement history (including voided edges), Maintenance events and schedules, Runtime, in-scope registry entries and references. Exactly which facts are destroyed vs retained must be settled before schema freeze.

**Deletion scope warning:** Purge of the *Device Lifecycle live canonical Asset* must not promise erasure from previous downloaded backups, Home Assistant backups, Recorder, logs or third-party integrations. Even a restored pre-purge backup may contain that Asset. The contract must state this explicitly. Guaranteeing irrevocable deletion across independent old backups would require a separate persistent revocation/trust mechanism; **not assumed**.

**Entity cleanup:** Purge and manual HA "delete device" behavior are different workflows. Only DL-owned Device Registry and Entity Registry records may be removed under validated ownership; removal is not proof Recorder history was erased. Entity Registry user customizations and orphaned IDs must be considered. Determine whether and how HA's \`async_remove_config_entry_device\` is appropriate without allowing accidental Asset Purge from a registry button.

## 7. Schema, migration and compatibility rules

- Store **4.1 is exact-shape**; no top-level, Asset or Purchase field may be appended as a "compatible" informal extension. A tombstone collection or purge metadata requires a deliberately versioned Store migration and a new validation contract.
- Decide schema number only after the frozen complete schema and compatibility matrix are defined; do not choose a target version just from the feature label 0.9.0.
- Every supported source version requires: read-only preflight -> pure deterministic transform -> full target validation -> durable write/readback -> publish. Never destructively rewrite unknown/newer data.
- Historical migration tests must cover 1.1, 1.2, 2.1, 3.1 and 4.1 where applicable; explicit expected unsupported/downgrade paths. Preserve permanent IDs, full history, Runtime, entity identities where safely possible.
- Export format version, Store version and integration release version are independent dimensions with their own compatibility matrix.
- Establish semantics for restored pre-purge backups, tombstone collisions and cross-instance conflicting \`DLxxxx\` counters. No automatic merge.

## 8. Failure model and verification gates

| Gate | Required evidence |
| --- | --- |
| G0 architecture | Decision register closed for blocking items; independent adversarial review, owner adjudication and explicit design freeze |
| G1 logical backup | Exact same-snapshot export determinism, stable identities, no forbidden data, limits and integrity checks; Runtime and ConfigSubentry consistency under concurrent mutation |
| G2 clean restore | Full round trip including allocation counter, Purchase/Subentries, lifecycle/replacements, Archive, Runtime totals, Maintenance and provenance; no foreign HA modifications or spurious entities |
| G3 failure recovery | Crash/fault injection before and after each persistent side effect, corrupted/truncated/unsupported backup, checksum mismatch, collision, missing external link, stale preview, full-disk/write failure, cancellation/restart; no partial success |
| G4 purge/tombstones | Dependency matrix, repeated/no-op policy, purge preconditions, never-reuse guarantees within lineage, retained historical-reference validity, owned-registry cleanup, restored-old-backup scenario |
| G5 real HA | Clean Test HA round trip and a rehearsed recovery on \`ha-ai-lab\`, evidence before/after for UUID/ID, histories, Runtime totals, Maintenance, subentries, device/entity ownership and duplicates |
| G6 release | Finnish/English UX, documentation/limits, CI/ruff/pytest, HACS Action, Hassfest, compatible HA versions; no unsupported data-loss or blocker |

**No G0 pass, no implementation authorization; no G2/G3 pass, no Purge approval; no G5/G6 pass, no 0.9.0 release.** Marketplace default submission remains blocked until #17's real-world restore evidence and a released build are accepted.
